## 总体判断

保留 Markdown 作为权威来源以及现有的领域库、服务契约、提供方和消费方划分。宿主承担会话、模型接入、权限与客户端入口，插件实现小说领域流程。当前最值得修的是跨模块契约：一次操作可以成功返回，但原稿、维护覆盖或工作台呈现会与作者预期不一致。优先修复发布产物和原稿安全，其次是改稿后的待办、维护失败可见性和章序一致性。

审查基线为 `cfda847`，宿主依赖为 `0.2.2-rc.1`。先按写作流程、治理、工作台与存储四条路径审查，再逐项回查实际调用、失败条件和既有裁定。P1 表示应优先修复的原稿、确认或内容正确性问题，P2 表示可恢复的流程错误或错误覆盖信号，P3 表示有明确依据但影响较轻的维护成本。

## 经复核的问题

| 编号 | 优先级 | 发现与证据 | 改进与验收 |
|---|---|---|---|
| R1 | P1 | **导出可以覆盖原稿。** `output_path` 允许任意项目内相对路径，服务通过词法范围检查后直接 `writeFile`。在临时作品中指定现有章文件，实测该章被合并后的导出文本覆盖。审批文案只说明导出写文件，服务也未区分权威资料和导出物。见 `packages/writer-tools/src/index.ts:27`、`:504`，`packages/writer-export/src/index.ts:100`。 | 在导出服务保护作品权威路径，默认限制到导出目录，自定义目录使用前校验。明确同名覆盖语义并采用原子写入。验收需覆盖正文、作品资料和待办路径均拒绝写入，以及旧导出物在写失败时仍完整。 |
| R2 | P1 | **工作台“提出修改”没有传递选区边界。** 入口只给助手发送自然语言要求，未绑定原文选区。助手未传 `selection` 时，补丁全失配仍可走整章生成并保存。现有冒烟检查草稿追加。见 `packages/writer-ui/src/client/Panel.tsx:81`、`packages/writer-engine/src/index.ts:614`、`:644`、`packages/writer-ui/scripts/studio-browser-check.mjs:182`。 | 工作台明确提供局部和整章两种范围。局部路线把原文和版本交给现有选区协议，无法定位时重新选区。补充从工作台到写入工具的验收，断言区外逐字一致，整章改稿由作者明确选择。 |
| R3 | P1 | **无关改稿会使仍成立的待确认建议失去有效入口。** 旧抽取作为防重参考，提示要求模型省略仍成立的条目，新缓存随后替换旧抽取。工作台又只允许当前章稿哈希对应的建议发起确认。用真实存储和测试模型复现仅改后一行后，仍成立的事实只留在过期节。见 `packages/writer-engine/src/index.ts:191`、`:247`、`packages/writer-engine/src/prompts.ts:155`、`packages/writer-ui/src/client/actions.ts:44`。 | 用已确认权威记录做防重。未确认候选须在新版正文中重新找依据，并以新版哈希投递。验收覆盖仍有效、已移除和已确认三种候选。 |
| R4 | P1 | **抽取缺节或坏条目可被记成维护完成。** 解析时丢弃坏条目、忽略非数组节，验证把缺节当空数组。定向重试少回目标节也会通过。注入畸形对象或错误重试回执，均可让坏结果落为完整缓存，后续重算走 `up-to-date`。见 `packages/writer-domain/src/maintenance.ts:71`、`:128`、`packages/writer-engine/src/index.ts:214`。 | 对本轮要求的节区分明确空数组、缺节、错误形状和部分有效。只重试失败节，保留已通过内容。达到重试上限时标记部分完成并让读者看到缺项。 |
| R5 | P1 | **早章的伏笔可见性在三个入口各有口径。** 检索对终态伏笔直接放行，因此早章可以召回后章才回收的档案。写作组装主要依赖计划锚，计划早、实际埋设晚时可注入档案正文。单章审稿则遇到未来实际锚就排除整条，可能遗漏早已埋设的部分。纯函数探针复现前两种。见 `packages/writer-domain/src/rag.ts:219`、`packages/writer-domain/src/index.ts:459`、`packages/writer-engine/src/review.ts:71`。 | 共用按目标章投影的伏笔规则，区分写作计划与作者已可见的事实，按章锚控制状态、里程碑和说明。无法区分时间的整段档案先保守使用。验收须回到同一伏笔的埋设前、埋设后和回收后三个时间点。 |
| R6 | P2 | **全书扫描会把缺失覆盖当成完整。** 服务端目录扫描把所有目录异常等同空目录，对坏章只记日志。临时作品含三份章文件，其中一份元数据损坏，导出成功返回两章且未报告遗漏章节。工作台另将宿主列表失败等同目录缺失，也未披露列表截断。注入失败响应可让有章项目显示为零章且提示规划。见 `packages/writer-store/src/index.ts:629`、`packages/writer-export/src/index.ts:62`、`packages/writer-ui/src/client/load.ts:145`、`:245`。 | 区分目录确实不存在、不可读、个别文档无效和截断。导出发现章节覆盖缺口时阻断或明确要求作者接受缺章；工作台提示覆盖范围，停止给出首章指引。写作和审稿材料也应带来源覆盖信息。 |
| R7 | P2 | **旧版本维护抛错时，新版自动维护会被一起跳过。** 新保存复用旧版在飞任务，最新版重读和补跑只在旧任务成功后发生。门控测试中，等待旧版模型的同时触发新版维护，再令旧版超时，两个调用失败且排空后无新版结果。见 `packages/writer-engine/src/index.ts:88`、`:149`。 | 同章合并记录最新请求，旧版失败后仅对可确认的新版本补跑一次。保持取消语义和失败披露。测试旧版失败、新版成功以及同版失败不自循环。 |
| R8 | P2 | **全书一致性检查缺少跨批对照，且只隔离解析故障。** 两批测试中，钥匙销毁与次日完好的两段正文从未同时送审，报告未披露这类比较的覆盖缺口。全书章节 ID 校验只能证明引用对象存在。另一测试中，第一批成功、后一批模型超时，已收集的发现及随后的确定性体检均未返回。见 `packages/writer-engine/src/index.ts:345`、`:381`、`packages/writer-domain/src/consistency.ts:104`。 | 披露逐批与跨批覆盖的区别，允许范围外引用作为待核线索，高危冲突通过定向复核引用两侧原文。保留成功批次和确定性结果，单列失败范围，取消继续传播。 |
| R9 | P2 | **实际伏笔落点可写入非法章号、缺失章或倒序。** 测试通过真实存储和已注册工具写入不存在的埋设章、早于埋设的回收章及非法里程碑章号。通用实体更新没有等价伏笔校验。见 `packages/writer-tools/src/index.ts:84`、`:200`。 | 计划锚可指未写章节，已发生锚校验格式、正文存在和时间顺序。专用与通用入口共用校验。对旧数据给出诊断，保留原始资料供作者修正。 |
| R10 | P2 | **章身份和章序还未形成统一契约。** 写作目标根据文件 ID 选大纲、算防剧透边界，历史章、审稿和导出则允许元数据 `number` 参与章序。探针中 `020.md` 写了 `number: 1`，其正文可作为第 003 章的前文进入写作和检索。见 `packages/writer-engine/src/index.ts:694`、`:726`、`packages/writer-domain/src/index.ts:399`、`packages/writer-domain/src/rag.ts:215`、`packages/writer-export/src/index.ts:31`。 | 先决定文件 ID 是否就是叙事章序，并在服务端和工作台统一。已有不一致、重复、缺号应可诊断。做一组共享样例，验证大纲、前文、检索上限、审稿与成书顺序。 |
| R11 | P2 | **初始化重试可以把半写文件视为完成。** 用合法初始化标记和未闭合的 `project.md` 模拟中断，状态先报可重试，重试后报就绪而损坏文件原样存在。模板直接写目标路径，重试只检查普通文件类型。见 `packages/writer-store/src/project.ts:125`。 | 模板完整写入同目录临时文件，再以不覆盖方式发布。恢复时提示可识别的损坏项，保留用户已经编辑的内容，覆盖落盘中断及恢复验收。 |
| R12 | P3 | **工作台的首次快照与监听之间存在窗口。** 扫描先结束再挂监听，只有重连就绪才补扫。锁定版宿主的监听只发订阅后的变化，窗口内编辑可使工作台显示已监听却持有旧快照。见 `packages/writer-ui/src/client/useProject.ts:94`、`:128`。 | 首次就绪也对账，或先订阅再扫描。用确定性测试在首扫和就绪之间提交修改，断言无需另一次编辑即可更新。 |

## 功能与架构改进顺序

1. **保护原稿和写作确认。** 先修导出路径和缺章回执，再把工作台的改稿范围接入已有选区协议。紧接着修维护形状校验、待确认候选续接与新版补跑。以临时真实作品覆盖整条路径，从改稿到审稿、维护、确认和导出。
2. **让同一材料在各入口有相同含义。** 统一章号与伏笔章锚，明确资料不可见、未读取、被截断及全批／部分失败的表达。先提取共享领域规则，保持 Markdown 文件和现有插件接口可渐进兼容。工作台应复用维护缓存形状校验，将摘要、拒收原因与可确认建议分别呈现。核心服务还有已弃用的通用派生文件接口，可在下一次兼容性调整中从公开契约移入存储包，保留现有业务方法。见 `packages/writer-ui/src/client/load.ts:350`、`packages/writer-ui/src/client/overview.ts:154`、`packages/writer-core/src/index.ts:102`。
3. **补长篇创作闭环。** 第一项是只读改稿影响清单：用变更摘要查后章正文、关键事件、人物时间线、关系和伏笔，引用原文供作者决定。现有区间派生重算解决重新计算，补上影响定位才形成流程。其次加带正文原句和章稿哈希的新伏笔候选，以及保留原话和处理去向的灵感整理技能。沿用上轮裁定的人工确认与 Markdown 归档。
4. **用大稿件数据决定性能投入。** 目前服务端列表每次仍触发全量目录和状态扫描，工作台文件变化也会重扫和读取多类文件。有现成解析缓存可用。先记录 100 章、500 章下的首次打开、单文件改动刷新和检索耗时，再按测量结果考虑逐文件刷新、按需读取和清理长驻会话缓存。见 `packages/writer-store/src/index.ts:597`、`packages/writer-ui/src/client/load.ts:218`。
5. **完成交付验证。** 先用独立模型与准备好的作品记录早章防剧透、跨批一致性和确认准确性。按发布清单另走干净 Electron profile，验证首轮前建书、真实桌面草稿、局部改稿和真人拒绝／批准导出。嵌套章节兼容、独立语义召回和宿主升级仍按既有裁定分别安排。
